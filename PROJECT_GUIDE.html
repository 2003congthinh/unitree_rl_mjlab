unitree_rl_mjlab · project guide

How a Unitree robot learns to walk and dance in this repository

This page follows the code from the first command you type to the moment a real G1 humanoid takes a step. It explains each stage, the files involved, and how the functions call one another.

Python · runs during training C++ · runs on / next to the robot data file passed between stages

What this project does

Unitree sells legged robots: the quadrupeds Go2, A2 and As2, and the humanoids G1 (29 or 23 joints), H1_2, H2 and R1. Nobody writes the walking controller for these robots by hand here. A neural network learns it by trial and error inside a physics simulator, and the finished network is then copied onto the robot.

The repository supports two skills:

  • Velocity tracking. The robot receives a command such as "walk forward at 0.8 m/s and turn left at 0.3 rad/s" and must follow it on flat or rough ground. All seven robots can learn this.
  • Motion imitation. The robot watches a recorded human motion, for example a dance, and copies it with its whole body. This follows the BeyondMimic method and is set up for the G1 (29 and 23 DoF).

The heavy lifting is done by two libraries this repo builds on. mjlab runs thousands of copies of the robot in parallel on the GPU using MuJoCo-Warp physics and provides the "manager" framework (observations, rewards, and so on). rsl_rl provides the PPO learning algorithm. This repository supplies the robot models, the task definitions (what to observe, what to reward), the training scripts, and the C++ program that runs the trained network on the real hardware.

The README summarises the work as Train → Play → Sim2Real. This guide uses the same three stages.

RL in two minutes

Reinforcement learning (RL) trains a policy: a function that looks at what the robot senses right now and decides what to do next. Here the policy is a small neural network (three layers of 512, 256 and 128 neurons).

Fifty times per second the loop goes like this. The simulator hands the policy an observation: a vector of numbers such as the body's tilt, joint angles, joint speeds and the current command. The policy outputs an action: one number per joint, which becomes a target angle for that joint's motor. The simulator moves the physics forward 20 ms and computes a reward, a score that is high when the robot did what we wanted (followed the command, stayed upright) and low when it did something bad (fell, slipped, jerked its joints). If the robot falls, the episode terminates and that copy of the robot is reset.

The PPO algorithm adjusts the network's weights so that actions leading to more total reward become more likely. Because the simulator runs 4,096 robots at once, the network sees millions of steps per minute and learns in hours instead of years.

Two networks are trained together. The actor is the policy and only sees what a real robot could measure. The critic estimates how good a situation is and is allowed extra "privileged" information (true body velocity, foot contact forces) that only the simulator knows. Only the actor is copied to the robot.

Path 1 · Training a walking policy

Everything starts with one line:

python scripts/train.py Unitree-G1-Flat --env.scene.num-envs=4096

Step 1: the task catalogue is filled. main() in train.py executes import src.tasks. That package's __init__.py calls mjlab's import_packages, which imports every sub-folder. Each robot folder, for example src/tasks/velocity/config/g1/__init__.py, then calls register_mjlab_task(...) with four things: a task id ("Unitree-G1-Flat"), an environment config for training, an environment config for playing, an RL config, and a runner class. After the import, mjlab's registry knows every task, and scripts/list_envs.py can print them.

Step 2: the configuration is assembled. TrainConfig.from_task("Unitree-G1-Flat") fetches the registered configs. The environment config was built by unitree_g1_flat_env_cfg(), which itself calls unitree_g1_rough_env_cfg(), which starts from the robot-independent template make_velocity_env_cfg() and fills in G1-specific names (the pelvis for the height scanner, the ankle links for foot contacts, the torso for orientation penalties) and the G1 motor model from get_g1_robot_cfg(). Any --env.* or --agent.* flag on the command line overrides a field of this config through the tyro library.

Step 3: the run is launched. launch_training() creates the log folder logs/rsl_rl/g1_velocity/<date_time>/, selects GPUs, and calls run_train() directly (one GPU) or once per GPU through torchrunx.

Step 4: the world is built. run_train() creates ManagerBasedRlEnv(cfg.env). mjlab compiles the robot's MJCF, the terrain and the sensors into one MuJoCo model, copies it 4,096 times on the GPU, and creates one "manager" per config section (observations, actions, commands, rewards, terminations, events, curriculum). The env is wrapped in RslRlVecEnvWrapper so rsl_rl can use it.

Step 5: learning. The task's runner, VelocityOnPolicyRunner, is created and runner.learn() starts the PPO loop: collect 24 steps from every robot (about 98,000 transitions), update the networks for 5 epochs, repeat up to 10,001 times. Every 100 iterations save() writes model_<iter>.pt and also exports the actor as policy.onnx, the file the robot will use.

Inside one control step

The physics runs at 200 Hz (timestep 0.005 s) but the policy only decides every fourth physics step (decimation = 4), so the policy runs at 50 Hz. Each call to env.step(actions) runs the managers in a fixed order. The diagram is worth reading slowly, because every function in src/tasks/*/mdp/ plugs into one of these boxes.

Observations. For the G1 velocity task the actor receives the angular velocity from the pelvis IMU, the gravity direction in the body frame (which tells it how tilted it is), the three-number command, a gait clock phase (sine and cosine of a 0.6 s cycle), joint angles relative to the default pose, joint velocities, and the previous action. On rough terrain it also gets a 17×11 grid of ground heights from a downward ray-cast sensor. Uniform noise is added to each term so the network learns to cope with imperfect sensors. The critic gets all of that without noise, plus the true linear velocity, foot heights, foot air time, contacts and contact forces.

Actions. The network outputs one number per joint. JointPositionAction turns it into a target angle: target = default_angle + scale × action. For the G1 the scale per joint is 0.25 × torque_limit / stiffness (computed in g1_constants.py), so an action of 1.0 asks for about a quarter of that motor's torque. The motors themselves are simulated as PD controllers whose stiffness and damping are derived from the real rotor inertia, tuned to a 10 Hz natural frequency.

Commands. UniformVelocityCommand draws a random target (forward speed, sideways speed, turn rate) every 3 to 8 seconds. 5 % of robots are told to stand still. Some robots get a heading target instead of a turn rate and a small proportional controller converts heading error into turn rate.

Events and domain randomisation. At start-up every robot gets random foot friction (0.3–1.6), a random joint-encoder offset and a shifted torso centre of mass. During the episode it is shoved every 5–6 seconds. At reset its position and heading are randomised. This variety is what lets a network trained in simulation survive the differences of the real world.

Curriculum. Two curricula make the task harder as the robot improves. terrain_levels_vel moves a robot to a harder row of terrain when it walked far enough and to an easier one when it walked less than half of what its command asked. commands_vel widens the speed ranges after 120,000 steps (5,000 iterations × 24).

What the robot is rewarded for

The reward is the only way to tell the robot what "good walking" means. It is a weighted sum of terms; each term is a function in src/tasks/velocity/mdp/rewards.py (or mjlab's built-ins) returning one number per robot. Positive weights are bonuses and negative weights are penalties. The tracking terms use the shape exp(-error² / std²), which gives 1.0 for perfect tracking and falls smoothly toward 0.

Path 2 · Teaching a dance (motion imitation)

Imitation needs a reference: a recording of what the robot should do. The repo ships one, src/assets/motions/g1/dance1_subject2.csv: 3,945 rows at 30 frames per second. Each row holds the root position (x, y, z), the root orientation as a quaternion, and 29 joint angles. A human dance was already retargeted onto the G1's skeleton before it reached this file.

Preparing the reference. The CSV only contains joint angles, but the rewards compare the positions and velocities of 14 body parts (hands, feet, knees, torso…). scripts/csv_to_npz.py computes them. Its MotionLoader resamples the clip from 30 to 50 fps (linear interpolation for positions, SLERP for the rotation) and estimates velocities by finite differences. run_sim() then places a single simulated G1 in each pose in turn, without running physics, and calls sim.forward() so MuJoCo computes forward kinematics: the world pose and velocity of every body. The results are stacked into arrays and saved as an .npz.

python scripts/csv_to_npz.py --robot g1 --input-file src/assets/motions/g1/dance1_subject2.csv \
       --output-name dance1_subject2.npz --input-fps 30 --output-fps 50
python scripts/train.py Unitree-G1-Tracking-No-State-Estimation \
       --motion_file=src/assets/motions/g1/dance1_subject2.npz --env.scene.num-envs=4096

The .npz is a dictionary of arrays (T = frames, J = joints, B = bodies):

KeyShapeMeaning
fps(1,)Frame rate of the file (50).
joint_pos(T, J)Joint angles in radians.
joint_vel(T, J)Joint angular velocities.
body_pos_w(T, B, 3)World position of every body link.
body_quat_w(T, B, 4)World orientation of every link, quaternion w-x-y-z.
body_lin_vel_w(T, B, 3)World linear velocity of every link.
body_ang_vel_w(T, B, 3)World angular velocity of every link.

Training. train.py notices that the task has a "motion" command and copies the --motion_file path into it. The MotionCommand term then works like a video player with one playhead per simulated robot. Each step it advances the playhead by one frame and exposes the reference pose at that frame. The policy observes the reference joint angles and velocities plus the orientation of the reference torso relative to its own. The rewards compare reference and robot: torso position and orientation, the 14 body positions and orientations, and their velocities, each as exp(-error²/std²).

Two ideas make this work. Reference state initialisation: when a robot is reset, it is teleported onto the reference at some frame (with small random noise), so it does not have to learn the first second of the dance before it can practise the tenth. Adaptive sampling: the clip is cut into one-second bins and the code counts in which bins robots fall. New episodes start more often in the bins that cause failures, so practice concentrates on the hard moves.

Body positions are compared after re-centring the reference on the robot (body_pos_relative_w): the reference is shifted and turned so that its torso has the robot's horizontal position and heading. This keeps the robot from being punished for drifting a few centimetres across the floor while it dances correctly.

There are two variants of the G1 task. Unitree-G1-Tracking lets the actor see the torso's position error and the body's linear velocity. A real robot cannot measure either reliably without a separate state estimator, so Unitree-G1-Tracking-No-State-Estimation removes them; that is the one meant for deployment. When saving, MotionTrackingOnPolicyRunner exports both a plain policy.onnx and a second ONNX file that embeds the whole reference motion.

Checking the result: play.py

python scripts/play.py Unitree-G1-Flat --checkpoint-file=logs/rsl_rl/g1_velocity/<run>/model_10000.pt

run_play() loads the play version of the environment config, created by the same env_cfgs.py function with play=True: episodes never time out, sensor noise and random pushes are off, the curriculum is off, and on rough terrain a 5×5 grid of random terrain is used. It builds the runner, loads only the actor weights from the checkpoint, and asks for an inference policy. Then it hands the environment and the policy to a viewer: the native MuJoCo window when a display is available, otherwise the browser-based Viser viewer.

In the viewer you see the robot plus debugging drawings produced by the code. For velocity tasks, UniformVelocityCommand._debug_vis_impl draws arrows above the robot: blue and green for the command, cyan and light green for the actual velocity. In Viser, create_gui() adds sliders so you can drive the robot yourself. For tracking tasks, MotionCommand._debug_vis_impl draws a translucent green "ghost" robot in the reference pose next to the real one.

You can also run --agent zero or --agent random to see the environment without any trained network, and --video to save an MP4 to <run>/videos/play/.

Path 3 · From simulation to the real robot

The robot's on-board computer does not run Python or PyTorch. The deploy/ folder contains a small C++ program per robot (for example deploy/robots/g1 → executable g1_ctrl) that loads policy.onnx with ONNX Runtime and re-implements just enough of mjlab to compute the same observations the network saw in training.

Start-up. main() reads config/config.yaml, connects to Unitree's DDS network on the interface you name (--network=lo for simulation, the Ethernet interface for the real robot), waits for the first LowState message (IMU, motor angles, joystick), checks the robot model, and starts a finite state machine.

The state machine. A robot must never jump from lying limp to running a neural network. CtrlFSM moves through safe states, switched by gamepad button combinations written in config.yaml and parsed by a small expression language (unitree_joystick_dsl.hpp).

  • Passive (State_Passive): motors only apply damping, so the robot can be handled safely.
  • FixStand (State_FixStand): every joint moves in a straight line over 2 seconds from where it is to the standing pose, using linear_interpolate().
  • Velocity (State_RLBase): runs the walking policy. The left stick sets forward/sideways speed, the right stick sets turn rate.
  • Mimic (State_Mimic): runs the dance policy while a C++ MotionLoader_ plays the .npz reference in time. When the clip ends it returns to Velocity.

Two loops at two speeds. Inside the RL states, a policy thread runs at 50 Hz exactly like the simulator. It reads sensors, builds the observation, runs the network, and turns the output into target angles. The FSM thread runs at 1 kHz and copies the latest targets into the motor command. The motor drivers then apply τ = kp·(q* − q) + kd·(dq* − dq) with the same gains used in training.

Sim-to-sim first. Before risking hardware, you build simulate/ into unitree_mujoco. It loads the robot scene named in simulate/config.yaml, runs MuJoCo, and a bridge thread (RobotBridge::run(), 1 kHz) pretends to be the robot: it converts incoming LowCmd messages into motor torques with the PD formula and publishes the simulated sensors as LowState. Because g1_ctrl cannot tell the difference, the very same binary later runs on the real robot by changing --network.

How Python and C++ agree

The network only works if the robot feeds it numbers in exactly the order, scale and units it saw during training. That contract lives in deploy/robots/<robot>/config/policy/<task>/params/deploy.yaml: the policy step time, joint order, PD gains, default pose, action scale and offset, and the list of observation terms. The table pairs the G1 velocity task's training terms with their C++ counterparts.

The rough-terrain policy also needs height_scan, which the C++ side does not provide, so the flat-terrain policy is the one to deploy. The PD gains in deploy.yaml (for example 40.2 and 99.1 N·m/rad for the hip joints) are the same numbers g1_constants.py computes from rotor inertia, and the action offset equals the default pose, mirroring use_default_offset=True in training.

Pictures and what they tell you

The repository has no notebooks and no plotting code. Its images are the eight animated GIFs in doc/gif/, shown in the README. They come in pairs: one recorded in simulation and one on the physical robot. No script in the repo writes GIF files directly. The simulation clips are recordings of scripts/play.py with a trained checkpoint (adding --video makes VideoRecorder save an MP4 under logs/rsl_rl/<experiment>/<run>/videos/play/, which can be converted to GIF). The real clips were filmed while the robot ran the C++ controller from deploy/robots/<robot>.

Read each pair as one experiment. The left image answers "did training produce the behaviour we wanted?" The right image answers "does that behaviour survive the jump to real hardware?" Differences between them are the sim-to-real gap that the domain randomisation in the training config is meant to close.

Things to watch out for

Reading the code closely turned up a few behaviours that are easy to trip over. They are also noted in the source comments.

play.py without --checkpoint-file crashes. The fallback branches read cfg.wandb_run_path and cfg.registry_name, which do not exist in PlayConfig, so you get an AttributeError instead of a helpful message. Always pass a checkpoint path, and a motion file for tracking tasks.

The C++ fall detector is disabled. mdp::bad_orientation() in deploy/include/isaaclab/envs/mdp/terminations.h has its check commented out and always returns false. If the robot falls while running a policy, it will not switch to Passive by itself. Keep a hand on the LT + B combination.

Some local classes are shadowed by mjlab's copies. velocity_env_cfg.py imports UniformVelocityCommandCfg and tracking_env_cfg.py imports MotionCommandCfg from mjlab, not from this repo's mdp/. The local files are near-identical copies, so behaviour matches, but editing the local command classes alone will not change training. Likewise, the G1 tracking config uses mjlab's built-in G1 asset rather than src/assets/robots/unitree_g1.

Observation order is a contract. If you add, remove or reorder an observation term in a Python env config, you must update the matching deploy.yaml in the same order, or the network on the robot will receive scrambled inputs.

Glossary

policy / actor
The neural network that maps observations to actions. The only part copied to the robot.
critic
A second network that estimates future reward; used only during training and allowed privileged inputs.
PPO
Proximal Policy Optimization, the learning algorithm (from rsl_rl) that updates the networks.
episode
One attempt by one simulated robot, from reset until it falls or time runs out.
decimation
Number of physics steps per policy step (4 here: 200 Hz physics, 50 Hz policy).
MJCF
MuJoCo's XML format describing a robot's links, joints, meshes and sensors.
DoF
Degrees of freedom; here the number of actuated joints (G1 has 29 or 23).
PD controller
Motor law τ = kp·(q* − q) + kd·(dq* − dq); the policy sets the target angle q*.
anchor body
The body used as reference frame for imitation; the G1 torso.
domain randomisation
Randomising friction, mass, sensor bias and pushes in simulation so the policy copes with the real world.
curriculum
Gradually raising task difficulty (terrain roughness, speed range) as the robot improves.
ONNX
A portable file format for neural networks, run on the robot with ONNX Runtime.
DDS
The publish/subscribe network protocol Unitree robots use for LowCmd and LowState messages.
FSM
Finite state machine; the deployment program's safe sequence of modes.
sim2sim / sim2real
Testing the deployment program first against a separate simulator, then on the physical robot.
